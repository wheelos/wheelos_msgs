# Bzlmod and Bazel design

## Module boundary

This repository publishes one Bazel module:

```starlark
module(
    name = "wheelos_msgs",
    version = "0.1.0",
    compatibility_level = 1,
)
```

Message directories are Bazel packages inside that module. They are not
independent Bazel modules or external repositories.

```text
wheelos_msgs/
  MODULE.bazel
  BUILD
  wheelos_msgs/
    BUILD
    audio_msgs/BUILD
    basic_msgs/BUILD
    ...
```

This keeps version selection, protobuf dependencies, visibility, and release
management in one place. A directory becomes a separate module only when it
needs an independent version, owner, compatibility policy, and release
cadence.

## Consumer usage

Consumers declare the module once:

```starlark
bazel_dep(name = "wheelos_msgs", version = "0.1.0")
```

Use the public aggregate targets from the `wheelos_msgs` Bazel package:

```starlark
cc_library(
    name = "demo_cc",
    deps = [
        "@wheelos_msgs//wheelos_msgs:audio_msgs_cc_proto",
    ],
)

py_library(
    name = "demo_py",
    deps = [
        "@wheelos_msgs//wheelos_msgs:audio_msgs_py",
    ],
)
```

For a target that needs every message:

```text
@wheelos_msgs//wheelos_msgs:wheelos_msgs_cc_proto
@wheelos_msgs//wheelos_msgs:wheelos_msgs_py
```

The target syntax is always:

```text
@wheelos_msgs//wheelos_msgs:<target>
```

Do not create aliases such as `@wheelos_msgs.audio_msgs`. A repository
alias changes the apparent repository name but does not create a package,
version boundary, or independent dependency graph.

## Target layers

Each message package has generated language targets:

```text
audio_proto              proto_library
audio_cc_proto           cc_proto_library
audio_py_pb2             py_proto_library
audio_msgs_cc_proto      package C++ aggregate
audio_msgs_py            package Python aggregate
```

The package aggregates are generated by
`scripts/tools/proto_build_generator.py`. The `wheelos_msgs/BUILD` file exposes
stable aliases and full-repository aggregates. Consumers should depend on the
aggregate targets unless they intentionally need one generated file.

Both levels are public: use `//wheelos_msgs:<name>_msgs_cc_proto` or
`//wheelos_msgs:<name>_msgs_py` for a message-package aggregate, and use
`//wheelos_msgs/<name>:<message>_cc_proto` or
`//wheelos_msgs/<name>:<message>_py_pb2` for an individual generated message.

## Protobuf import namespace

Proto imports use the public `wheelos_msgs` namespace:

```proto
import "wheelos_msgs/basic_msgs/header.proto";
```

The Bazel source packages remain under `wheelos_msgs/`, but generated C++ and
Python paths use `wheelos_msgs`. The Python namespace is:

```python
from wheelos_msgs.audio_msgs import audio_pb2
```

The generated C++ include path likewise uses:

```cpp
#include "wheelos_msgs/basic_msgs/header.pb.h"
```

The protobuf `package apollo.*` declarations are independent of Bazel and
Python package names and should not be changed as part of this layout.

## Compatibility policy

Changing a proto import path from `common_msgs/...` to `wheelos_msgs/...`
changes the descriptor file name, generated Python imports, and generated C++
header paths. This is a compatibility-sensitive change. Removing a proto file,
target, or message field is also a downstream breaking change. Such changes
require a documented migration and a major compatibility/version decision; do
not silently reuse a minor or patch release.

Before a release, review the diff for:

1. Removed `.proto` files or Bazel targets.
2. Removed or renumbered fields.
3. Changed protobuf import paths.
4. Changed generated Python import paths.
5. Changed public aggregate target names.

## Validation

Run the repository-wide Bazel build:

```shell
bazel build //wheelos_msgs/...
```

Validate the public aggregates:

```shell
bazel build \
  //wheelos_msgs:wheelos_msgs_cc_proto \
  //wheelos_msgs:wheelos_msgs_py
```
